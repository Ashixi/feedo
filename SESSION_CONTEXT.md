# 🧠 Feedo Protocol: Глибокий Контекст Сесії та Архітектурні Рішення

*Цей документ містить повний контекст поточної архітектури, прийнятих архітектурних рішень, ідеології проекту та стратегії його просування. Надішліть його ШІ на початку наступної сесії, щоб він миттєво "ввійшов у курс справи".*

---

## 🌍 1. Ідеологія: Web4 та "Єдиний Семантичний Граф"
В основі Feedo лежить амбітна візія (яку ми іронічно називаємо Web4) — створення єдиного, глобального децентралізованого мозку.
**Проблема сучасного Інтернету (не тільки Web3):** Мережі, платформи та блокчейни (Nostr, Farcaster, традиційні соцмережі) існують як ізольовані силоси. Пошук у більшості з них працює жахливо, базуючись лише на точному збігу слів, а не на сенсі.
**Рішення Feedo:** Головна ідея — Feedo створюється як фундаментальний протокол і базова інфраструктура, на якій розробники будуть будувати нові додатки (dApps) майбутнього. Це нативний **базовий шар даних (Semantic Data Grid)** зі стійкою до цензури P2P-мережею та AI-пошуком за сенсом. 
Але щоб подолати проблему "порожньої мережі" і швидко вийти на ринок (Go-To-Market), Feedo на початковому етапі "заковтує" дані з уже існуючих мереж (Nostr, Farcaster). Це наповнює глобальний граф життям з першого ж дня і створює ідеальний ґрунт для нових проектів.

---

## 🏗️ 2. Поточна Базова Архітектура
Архітектура протоколу розділена на кілька шарів, які спілкуються через локальний IPC (Protobuf):

1. **Feedo Core (Rust):**
   - Мережевий рівень на базі `libp2p` (Gossipsub, Kademlia DHT).
   - Зберігання локального P2P стану в `sled`.
   - Консенсус: **PBFT** (Practical Byzantine Fault Tolerance).
   - Erasure Coding (Reed-Solomon) для шардування контенту.

2. **Feedo API (Python):**
   - Бекенд на `FastAPI`.
   - Семантичний рушій: `SentenceTransformers` та векторна БД `LanceDB`.
   - Реляційна метадана: `SQLite`.

3. **Токеноміка (Solidity):**
   - Смарт-контракт `FeedoPayment.sol` (EVM).
   - Реалізує мікротранзакції та автовиплати валідаторам (PBFT Leaders) на основі оновлення Merkle Root (дерева Меркла).

## 🐎 3. Стратегія "Троянського Коня" (Protocol Bridges)
Найголовніше рішення цієї сесії стосувалося того, **як саме** інтегрувати Feedo з Nostr та Farcaster.
Замість того, щоб створювати "ще один міст" між існуючими мережами або просити розробників переписувати свої клієнти, ми використали стратегію "Троянського коня":

*   **Feedo не змушує клієнтів адаптуватися.** Натомість Feedo-нода сама "одягає маску" існуючої інфраструктури.
*   **Для клієнтів Nostr (Damus, Amethyst):** Наша нода виглядає як звичайний WebSocket Relay.
*   **Для клієнтів Farcaster (Warpcast, Primal):** Наша нода виглядає як звичайний gRPC Hub.

Завдяки цьому ми можемо прийти до розробників і сказати: *"Вам не треба нічого міняти. Просто додайте нашу ноду у список ваших релеїв/хабів, і ви миттєво отримаєте глобальний ШІ-пошук по всьому контенту"*.

## 🛠️ 4. Технічна Реалізація Гібридних Нод (Остання сесія)
Ми реалізували два окремих Rust-бінарники, які слугують "точками входу" (Ingress) для зовнішніх мереж. Усі вони побудовані за патерном **Транслятора**: вони приймають специфічний для мережі формат і неблокуюче (`tokio::spawn`) перенаправляють його локальному семантичному рушію.

### А. Nostr Ingress (`feedo_nostr.rs`)
*   **Інтерфейс:** Піднімає WebSocket сервер на порту `8080`.
*   **Логіка:** Слухає повідомлення `["EVENT", {...}]` (NIP-01). 
*   **Трансляція:** Бере текст посту, підпис та публічний ключ автора, формує структуру `FeedoBroadcast` (Protobuf) і відправляє POST-запит на `http://127.0.0.1:8041/local/publish`.

### Б. Farcaster Ingress (`feedo_farcaster.rs`)
*   **Інтерфейс:** Піднімає gRPC сервер (на базі `tonic`) на стандартному для Farcaster Hub порту `2283`.
*   **Протокол:** Імплементує `HubServiceServer` з `farcaster.proto`.
*   **Логіка:** Перехоплює метод `submit_message`, очікуючи `CastAddBody`.
*   **Трансляція:** Транслює ідентифікатор користувача у формат `farcaster_fid_{fid}`, щоб уникнути колізій з публічними ключами Nostr. Текст касту також відправляється на локальний API Feedo для векторизації та публікації у глобальний DHT.

## 🐳 5. Інфраструктура Розгортання (Docker)
Щоб ці гібридні ноди було легко розгортати операторам, ми розділили конфігурації:

*   **Базове ядро:** `docker-compose.yml` (тільки Rust Core + Python API).
*   **Nostr-міст:** Використовує `Dockerfile.hybrid` та `docker-compose.nostr.yml`. Запускає скрипт `start-hybrid.sh`, який паралельно піднімає `feedo-core`, `feedo-nostr` та `uvicorn`.
*   **Farcaster-міст:** Використовує `Dockerfile.hybrid-fc` та `docker-compose.farcaster.yml`. Запускає скрипт `start-hybrid-fc.sh`, який паралельно піднімає `feedo-core`, `feedo-farcaster` та `uvicorn`.

Усі конфігурації підключені до спільної бази `PostgreSQL` та використовують внутрішню мережу Docker для IPC взаємодії. Rust-бінарники успішно компілюються з feature-прапорцями (`--features nostr / farcaster`).

## 🔄 7. Життєвий цикл даних у Гібридній Ноді (Data Flow)
Щоб ШІ в майбутньому розумів повний маршрут даних, ось покроковий процес того, що відбувається, коли користувач (наприклад, з Nostr) робить пост:
1. **Прийом:** Користувач публікує подію у свій улюблений клієнт (Damus). Клієнт відправляє WebSocket-повідомлення `EVENT` на нашу гібридну ноду.
2. **Трансляція (Rust):** `feedo_nostr` перевіряє підпис, запаковує текст у `FeedoBroadcast` і шле POST-запит на `http://localhost:8041/local/publish`.
3. **Векторизація (Python):** `feedo-api` отримує запит, проганяє текст через локальну NLP-модель (`SentenceTransformers`) і отримує семантичний вектор (ембеддінг).
4. **Збереження (LanceDB):** Вектор зберігається у локальній базі `LanceDB` для блискавичного K-NN пошуку.
5. **Розповсюдження (Gossipsub):** Метадані та хеш відправляються назад у Rust-ядро, яке розсилає їх іншим нодам по всьому світу через P2P мережу (`libp2p`).
6. **Консенсус (PBFT):** Валідатори (Leaders) голосують за транзакцію, перевіряють її унікальність (щоб уникнути спаму) і записують в історію.

## 💰 8. Глибока Токеноміка та Смарт-Контракт
Смарт-контракт `FeedoPayment.sol` (написаний на Solidity для EVM-сумісних мереж, як-от Polygon) є серцем економіки Feedo.
* **Проблема:** Мікротранзакції за кожен пошуковий запит або векторизацію в блокчейні були б занадто дорогими.
* **Рішення (Автовиплати + Merkle Trees):** PBFT-лідер (головна нода в епоху) накопичує інформацію про те, хто скільки заробив (за зберігання, маршрутизацію або обробку запитів). В кінці періоду лідер генерує **Merkle Root** усіх балансів і записує лише цей корінь у смарт-контракт `FeedoPayment.sol`.
* **Claim:** Будь-яка нода може прийти до смарт-контракту, надати свій Merkle Proof і локально забрати свої зароблені токени, самостійно оплачуючи газ. Це робить систему ідеально масштабованою.

## 🧬 9. CRDT та Reed-Solomon (Технологічний фундамент)
* **CRDT (Conflict-free Replicated Data Types):** Ми використовуємо їх для динамічних станів, які часто змінюються (лайки, підписки, редагування профілів). Це дозволяє нодам оновлювати стан локально і миттєво без потреби чекати консенсусу всієї мережі. При синхронізації (Anti-Entropy) конфлікти вирішуються автоматично та математично правильно.
* **Reed-Solomon Erasure Coding:** Використовується для зберігання великих медіа-файлів (BLOBs). Замість того, щоб кожна нода зберігала 100% відео чи картинки (що вбило б мережу), файл розрізається на 45 шархів (shards). Для відновлення файлу достатньо отримати будь-які 30. Це гарантує "Data Availability" (доступність даних) без екстремального навантаження на окремі вузли.

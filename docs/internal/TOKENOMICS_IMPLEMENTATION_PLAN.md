## 1. Принципи (з існуючого концепту)

- Оплата в **USDC** (стабільна монета, ціль) — перехід з **USDT** пізніше, без волатильного внутрішнього токена.
- Глобальний спліт **5 / 5 / 90**:
  - **5%** — Foundation (розробка, маркетинг, аудити)
  - **5%** — Consensus validators (Top-21)
  - **90%** — Provider fee (ноди, що виконали фізичну роботу: Storage + Search)
- **Virtual accounting**: мікроплатежі рахуються off-chain, settlement — on-chain (cash-out через `PporTreasury.sol`).
- DID реєстрація — **безкоштовна**, дає 500 000 тестових кредитів.

## 2. Оплата: поповнення балансу (top-up)

### Ключове розуміння: DID вже = гаманець

DID-формат Feedo — `did:feedo:0x<адреса>` (secp256k1). `auth.py` вже перевіряє підпис через `personal_sign` + `Account.recover_message` — це MetaMask-сумісний підпис. Тобто DID і адреса гаманця — **одне й те саме** («той самий публічний ключ»).

### Чому без memo: `msg.sender` і є DID

Якщо DID = адреса гаманця, контракту не потрібне поле memo/DID — він дивиться на відправника:

```solidity
function deposit(uint256 amount) external {
    usdt.transferFrom(msg.sender, address(this), amount);
    emit CreditClaimed(msg.sender, amount);
    // eth_bridge: balance["did:feedo:" + msg.sender] += amount
}
```

### Флоу топ-апу

1. Юзер має Polygon-гаманець (MetaMask)
2. На сайті Feedo: «Підключити гаманець» → сайт отримує **адресу** (НЕ приватний ключ)
3. `DID = did:feedo:0x<address>` — автоматично
4. Реєстрація DID: 1 підпис `personal_sign` у MetaMask
5. Топ-ап: юзер шле USDT на контракт → `msg.sender = DID` → `balance += amount`
6. Кожен запит: SDK підписує через MetaMask автоматично

### Ключ = доказ володіння (не просто ідентифікатор)

DID (адреса) — публічна інфа, її легко дізнатись. Тому **сам DID нічого не доводить**: будь-хто, хто знає чужу адресу, міг би видати себе за неї і юзати на шару. Доказ володіння — це **підпис** (`personal_sign` → `recover_message` в `auth.py`).

Наслідок: **хто б не викликав SDK, він мусить тримати приватний ключ.** Звідси два контексти:

| Контекст | Де ключ | Покидає гаманець? |
|---|---|---|
| Браузер + MetaMask | всередині MetaMask (підпис там само) | ❌ Ні — ключ не потрапляє в JS |
| Сервер (SDK в env: AnythingLLM, Dify, backend) | в env-файлі | ✅ Так — юзер експортує ключ із гаманця |

Твердження «ключ ніколи не покидає гаманець» правдиве **лише** для браузерного флоу. Для серверного SDK ключ **мусить** бути в env — інакше не довести володіння DID.

### Реальна проблема: в env лежить ключ, який контролює USDT

Проблема не в тому, що ключ покидає гаманець, а в тому, що **той самий ключ** і фандить (тримає USDT), і підписує запити. Скомпрометований сервер = зловмисник забирає USDT.

Рішення — розділити **funding key** (гаманець з грошима) і **usage key** (підписує запити):

**Рівень 1 (прагматично, зараз): окремий «гарячий» гаманець для Feedo**
- Генеруєш окремий ключ лише для Feedo → кладеш в env → фандиш малу суму.
- Втрата env = втрата лише топ-апу, не основного гаманця. Нуль змін у коді.

**Рівень 2 (правильно, потім): делегація / session keys**
- DID лишається = гаманець (фандинг через `msg.sender`, без memo).
- Юзер **разово** підписує в MetaMask делегацію: «ключ K має право витратити до N кредитів до часу T від мого DID». K — **детерміновано виведений** з ключа гаманця (секція нижче), а не випадковий.
- В env лежить **K** (не funding key). `auth.py` перевіряє: підпис = K **і** K делегований DID.
- Компрометація K = максимум N кредитів, USDT недосяжні, делегацію можна відкликати.

Це backward-сумісно: `auth.py` приймає і прямий підпис (`recovered == DID`), і делегований.

### Деривація: DID = гаманець, usage key = виведений з ключа гаманця

Уточнена схема (виведений ключ **не** стає новим DID):

1. **DID = адреса гаманця** (`did:feedo:0x<0xW>`), без змін. Топ-ап працює сам собою: `msg.sender = 0xW = DID` → гроші автоматично падають на правильний DID. Без memo, без таблиці прив'язок.

2. **Usage key — виведений** з приватного ключа гаманця, це **інший** ключ:

```python
usage_sk = HMAC-SHA256(key=wallet_sk, msg="feedo/usage-key/v1") mod n   # 0xD = address(usage_sk)
```

3. **Делегація (одноразово, в момент виведення):** гаманець підписує «0xD — мій usage key»:

```
personal_sign("feedo delegate usage to 0x<0xD>")   # recover(sig) == 0xW — доказ від гаманця
```

   Consensus зберігає `(0xW → 0xD)`.

4. **В env — лише `usage_sk`** (виведений), НЕ ключ гаманця.

5. **Підпис запитів:** SDK підписує через `usage_sk`. `auth.py`: `recovered = 0xD` → дивиться делегацію `0xD → 0xW` → DID = `0xW`.

**Чому мережа розуміє, хто надіслав гроші:**
- Фандинг іде з гаманця `0xW`, а DID = `0xW`. Зв'язок тривіальний — `msg.sender` і є DID.
- Виведений ключ `0xD` існує **лише для підписів**, гроші на нього не кладуть. Неоднозначності немає.

**Два кроки, які не треба плутати:**
- **Виведення** `usage_sk` = HMAC від приватного ключа. Потребує самого ключа (офлайн/локально). З **підпису** ключ не вивести — nonce ECDSA випадковий, кожен `personal_sign` дає різний результат.
- **Делегація** = підпис гаманцем рядка про `0xD`. Це доказ володіння, а не генерація ключа.

**Безпека / відновлюваність:**
- HMAC односторонній: з `usage_sk` не відновити `wallet_sk` → USDC недосяжні при компрометації env.
- Втрата `usage_sk` = максимум кредити DID (опційно делегація з лімітом/терміном, як session keys).
- Втратив env → пере-вивів `usage_sk` з `wallet_sk` → той самий `0xD` → делегація досі дійсна.

**Контексти:**
- **Сервер:** вивів `usage_sk` один раз офлайн → в env → зареєстрував делегацію. Ключ гаманця на сервер не потрапляє.
- **Браузер:** MetaMask ключ не віддає → деривація не потрібна, MetaMask підписує напряму (DID = гаманець, як зараз).

### Чому без платіжних полів на сайті (комплаєнс)

Сайт лише показує адресу контракту + DID (інструкція, не форма). Сам платіж — у гаманці юзера:

- Немає PCI DSS (карткові поля відсутні)
- Немає KYC/AML тягаря (Feedo не збирає фіат → не money transmitter)
- Feedo не торкається фіатних рейок — тільки USDT напряму в контракт

### Що змінити в коді

| Компонент | Зміна |
|---|---|
| `sdk/typescript` | signer-абстракція: `new FeedoClient({ signer: provider.getSigner() })` замість `privateKey` |
| `client.ts` / `search.ts` | `myDid = did:feedo:${await signer.getAddress()}`; підпис через `signer.signMessage()` |
| `PporTreasury.sol` | `deposit(uint256 amount)` без DID (sender = DID) |
| `eth_bridge.rs` | при `CreditClaimed(sender, amount)` → `balance["did:feedo:"+sender] += amount` |

## 4. Розподіл доходу між нодами (ключова складність)

### Проблема

У P2P-флоу роботу виконують **кілька нод**, а не одна.

**Пошук:**
```
Клієнт → Нода A (ingress: embedding запиту + роутинг)
              → Нода B (storage: шукає у своєму шарді, повертає)
              → Нода A → Клієнт
```
- A: embedding + роутинг
- B: власне пошук по векторах

**Індексація:**
```
Клієнт → Нода A (embedding документа)
              → Нода B (зберігає вектор у своєму шарді)
```

**Питання:** як ділити 90% provider fee між A і B?

### Варіанти розподілу

| Варіант | Опис | Плюси | Мінуси |
|---|---|---|---|
| **A. 50/50** | Ingress і storage ділять порівну | Максимально просто | Не відображає реальні витрати |
| **B. Фіксований routing-%** | Ingress X% (напр. 20%), storage 80% | Просто, враховує що search дорожчий | Треба підібрати X |
| **C. Реальні витрати** | Кожна нода рахує CPU-час і заявляє його | Чесно | Складно, можна накрутити |
| **D. Окремий прайс на дію** | Embedding = X, search = Y, storage = Z | Найточніше | Найскладніше |

### Рекомендація (чернетка)

Почати з **варіанту B**: ingress отримує фіксований routing-відсоток, storage — решту. Відсоток підібрати емпірично.

## 5. Архітектура імплементації

### 5.1 Метринг (що коштує скільки)

**Єдина валюта — «кредит».** Один об'єднаний баланс для всього (пошук + зберігання), не два окремих.

Прив'язка: **1 запит = 1 кредит** (найчастіша операція = одиниця).

| Операція | Кредитів | Прив'язка до $ |
|---|---|---|
| 1 пошуковий запит | **1** | $0.0005 |
| 1 зображення (CLIP) | **2** | $0.001 |
| 1 ГБ зберігання / міс | **40** | $0.02 |
| 1 ТБ зберігання / міс | **40 000** | $20 |

Чому саме так, а не «1 ГБ = 1 кредит»: якщо прив'язати до гігабайта, то запит коштуватиме 0.025 кредита (дробове число). Запит — найчастіша операція, тому він = 1.

``` 
operation_cost = f(route, обсяг_даних, кількість_векторів)
```

### 5.2 Атрибуція (хто отримує кредит)

При платній операції нода записує ledger-подію:
- хто запитував (DID)
- скільки коштувало
- які ноди виконували роботу (ingress + storage + routing)

Події агрегуються consensus-шаром.

### 5.3 Balance check (консенсус = джерело істини)

Перед платною операцією — перевірка балансу DID. Недостатньо кредитів → відмова.

**Архітектура: консенсус = settlement, search-node = метринг.**

- **Консенсус** тримає ledger (істина) і виконує settlement — списує кредити, атрибутує оплату нодам.
- **Search-node** тільки *записує* ledger-події (хто запитував, скільки коштувало, які ноди працювали), але не «вигадує» собі оплату.
- Це і є anti-abuse: search-node не може сам собі нарахувати кредити, тільки повідомити про роботу.

Практично: розширити вже існуючий consensus-виклик у `auth.py` (`GET /did/{address}/balance`) — разом із перевіркою реєстрації перевіряти «баланс ≥ вартість операції». Окремий round-trip не потрібен, він уже є.

### 5.4 Cash-out

Consensus періодично генерує proof балансу ноди → оператор забирає USDT через `PporTreasury.sol`.

### 5.5 Що вже є (частково)

- `consensus-node` має `ledger` (баланси), `eth_bridge`, концепт `PporTreasury.sol`.
- `register_did` кредитує 500 000.
- `get_did_balance` віддає баланс.
- DID = адреса (`did:feedo:0x...`) + `personal_sign` — вже є в `auth.py` (основа топ-апу без memo, секція 2).
- **Бракує**: топ-ап через контракт, метринг + дедакт кредитів на search-node і storage-node.

## 6. Рішення та відкриті питання

### 6.1 Прийняті рішення

**Фінальний прайс-лист (платні операції):**

| Операція | Роут | Ціна |
|---|---|---|
| Пошук (text-in, Feedo ембедить) | `GET /query` | $5 / 10k запитів |
| Векторизація тексту | `POST /index_document` | $5 / 10k векторів |
| Векторизація зображень | `POST /index_image` | $5 / 5k векторів |
| Зберігання файлів | `POST /upload` | $20 / TB / місяць |
| Домен | `POST /name/register` | $5/рік або $100 назавжди |

Все інше — безкоштовно (download, delete, count, resolve, баланс, зберігання векторів).

**Два режими роботи (різні ціни):**

| Режим | Хто ембедить | Індексація | Пошук |
|---|---|---|---|
| **Text-in** (прямий SDK-юзер) | Feedo (e5-small) | $5 / 10k векторів | $5 / 10k запитів |
| **Vector-in** (Dify-подібні інтеграції) | зовнішній (OpenAI тощо) | **безкоштовно** (просто зберігання) | **$5 / 100k запитів** (~10× дешевше, бо без embedding) |

Логіка: у vector-in режимі Feedo **не робить** embedding (його робить зовнішня модель за свої гроші), тому:
- індексація = просто зберігання вектора = безкоштовно
- пошук = тільки пошук (без query-embedding) = ~10× дешевший

## 7. Репутація та динамічний rate limiting (відповідь на anti-abuse)

### Ідея

Замість фіксованого rate limit для всіх — **динамічний ліміт залежно від репутації DID**. Це одночасно вирішує:
- Anti-abuse (свіжий акаунт не може заспамити)
- Розподіл навантаження (великі клієнти рівномірно розподіляються по нодах)
- Комфорт великих клієнтів (соцмережа отримує 1000+ req/s без ручного апруву)

### Фактори репутації

| Фактор | Що вимірює | Чому важливий |
|---|---|---|
| **Вік акаунта** | час з моменту реєстрації DID | сибіл-ферма з тисячі свіжих DID одразу видна |
| **Фінансовий комітмент** | баланс USDT / куплена ліцензія ноди | гроші = не ферма |
| **Чиста історія** | відсутність abuse-флагів від нод | довів, що не спамить |
| **Обсяг без порушень** | скільки використав без скарг | реальне використання ≠ абуз |

### Тіри (чернетка)

| Тір | Rate limit | Вимоги |
|---|---|---|
| **Fresh** | 10 req/s | новий DID |
| **Active** | 50 req/s | 7+ днів, чиста історія |
| **Verified** | 500 req/s | USDT-депозит або ліцензія ноди |
| **Enterprise** | 1000+ req/s | великий USDT-комітмент + явна угода |

### Де зберігається репутація

Off-chain у consensus-леджері (поруч із балансами). Search-node запитує репутацію при перевірці DID і застосовує динамічний ліміт.

### Розподіл навантаження по нодах

- **SDK-рівень**: `NodeRouter` зараз пінить одну ноду. Додати round-robin / least-loaded вибір для високорепутаційних клієнтів — розкидає запити по кількох нодах.
- **Network-рівень**: ingress-нода може шардити запити на пірів при великому потоці.

### Відкриті питання (репутація)

1. **Sybil-стійкість репутації.** Якщо DID безкоштовні, можна нафармити тисячі акаунтів, витримати «вік» і отримати вищі ліміти. Ліцензія ноди ($1–5) — дешевий бар'єр. Чи достатньо комбінації «вік + гроші + історія», щоб ферма була нерентабельною?

2. **Як ноди повідомляють про abuse?** Якщо нода флагає юзера, а юзер сплачує — хто правий? Треба механізм оскарження / поріг флагів.

3. **Деградація репутації.** Якщо юзер довго не активний, чи падає його репутація? (Проти «виростив репутацію і продав акаунт».)

4. **Enterprise-тір.** Хто апрувить «великий USDT-комітмент»? Ручний процес чи автоматичний поріг?

### Виконано — usage key + айдентика через гаманець

- ✅ `consensus-node` `register_did`: реєстрація вимагає `personal_sign("feedo register <did>")` (доказ володіння).
